# Design

## Context

见 proposal.md。现有 `knowledge_entries` 保存与材料、班级关联的完整 UTF-8 正文；Go 服务端持有会话认证和班级身份，材料详情与下载已经按班级授权。第 3 课变更尚未归档，主力 `openspec/specs/` 仍为空，本次新增独立的 `knowledge-retrieval` 能力，不改已有行为。

## Goals / Non-Goals

**Goals:** 沿用当前数据库和会话，提供可运行、可验收的本班正文检索与原文出处；API 和页面使用同源路径。

**Non-Goals:** 本轮不建立向量索引、不调用嵌入或生成模型、不做混合排序。已有文件名筛选继续保留，与正文检索分开。

## Decisions

### 1. 在 Go 服务端按会话班级读取并匹配

`GET /api/retrieval?q=...` 先验证会话，再拒绝客户端携带的班级/角色覆盖字段，只读取当前 `class_id` 的 `knowledge_entries` 与同班 `materials`。匹配在 Go 中对 Unicode 字符做大小写折叠，`%` 和 `_` 均当普通字符。这样复用现有正文并避免 SQL `LIKE` 通配符改变查询含义。备选 MySQL 全文索引可改善大规模性能，但中文分词与索引迁移会扩大本次 MVP 范围。

### 2. 按原文字符位置生成出处

结果最多返回 20 条，每条给出材料 ID、标题、400 字符窗口计算出的段号、零起点且右开区间的字符范围和命中附近原文摘录。前端显示一基字符位置，点击结果通过已有受保护详情接口打开原文。索引以 Unicode 字符而非 UTF-8 字节计，中文位置可核对。备选持久化 `knowledge_chunks` 表是完整第 4 课方案，但本 MVP 可以从已有正文确定性地产生窗口，省去迁移和回填；后续向量检索再持久化切片。

### 3. 明确失败与空结果

查询去掉首尾空白后限 1–100 字符；空白或超长返回 400。匿名返回 401，伪造身份返回 403，数据库故障返回 503。无命中返回空数组，由前端显示明确提示。结果正文以普通文本渲染，不执行来源材料中的 HTML。

## Risks / Trade-offs

- [扫描本班正文的成本随材料总量增长] → 只作为教学 MVP，上传单文件已有大小上限，结果限制 20 条；后续可改为持久切片与索引。
- [窗口段号不是语义段落] → 明确用固定 400 字符窗口，提供精确字符范围和可打开的原文；后续切分策略可单独变更。
- [大小写折叠不等于语言学同义检索] → 界面明确提示输入原文词语；向量/语义能力留待后续。

## Migration Plan

无需数据库迁移，重建 API 与前端容器即可启用。旧材料和后续上传材料均从已有正文检索；回滚代码与容器时保留 MySQL 和上传卷。
